Preempt-Providence — e2e mirror demos

Browser mirrors of the Step 7 e2e suites. Each page runs the exact scenarios from its vitest twin against the same compiled core and renders the tested data (trees, fork arms, warnings, guard trips) as visible content with live PASS/FAIL results.

Demos

  • SSR receive → complete render — mirrors tests/e2e/ssr-render.test.ts. The page is generated by scripts/build-demo.mjs: the e2e input data is serialized by the framework into the preempt-initial-data document and embedded in the HTML, then re-resolved and rendered in-browser. Shows expected behavior, the expected document tree structure, the live rendered DOM, the resolved providers (the dock consumes the DISTINCT feed-a/feed-b sources — one state, both bindings), and PAR-5 parity vs the embedded server reference.
  • Loop-safety probes — mirrors tests/e2e/loop-safety.test.ts: A→B→A circles, component self-reference, dangling source/target, deep acyclic chains (compile actionable — depth is not a loop signal), single-parent enforcement — each with its expected behavior, the graph structure built, and the observed guard trip.
  • Component-driven rendering (bonus) — the only hand-written HTML is the skeleton and the #root placeholder; everything else is framework-rendered. Nodes carry target component references for type/children (populating descendants) and source references for the values in those children; every element shows the placement/component resolution it follows, and each test is a content node in the tree. Includes a working user pane: a component-provided after-compile handler populates it from session state — click Log in (mock login showing the predefined user) or Log out.
  • Mode toggle — SSR / client / markdown adapters — the same feature-matrix document rendered through three adapter modes (toggle bar). SSR: the server sends the full <app>…</app> HTML it rendered through the real SSRFragmentAdapter — inspect it in the devtools Response tab, then compare with the raw received string and the parsed mount on the page. Client: the browser re-resolves the serialized document (S4.2) with no server payload. Markdown: the raw editor source is embedded verbatim for manual inspection alongside the live parsed display. Every mode runs the identical shared feature-matrix checks plus its mode-specific ones. Served dynamically per ?mode= by scripts/serve-demo.mjs.
  • Fork stress — layered child-creation stress test (d2 · d4 · d6 · d8 · d9 · d10 · d11 · d12 · d14) — a demo-only stress test of the forking render system. A binary tree is built layer by layer, each layer adding 2 children per node through one of the four runtime child-creation mechanisms, cycling: placement → component values → component link → idempotent handler → repeats with different placement/component names. Depth dN has 2N − 1 nodes (d12 = 4095 nodes; the memoized, cycle-only parent-chain classifier keeps every layer actionable). d14 = 16383 nodes is the SCALING PROBE — the d12 totals are too fast to expose pipeline scaling (timer-drain + findEl fixes), so depth 14 re-exposes the pass-2 shape. Every node renders its stress:layers chain (depth + tree-back-to-root). The page uses ONLY core (dist/core/*) and handler code — no demo-side render machinery.
  • Path fork (static) — 22 prototypes, ONE path-enumeration pass — the fork-stress tree WITHOUT clones (placement-path-spec §5): the same 22-prototype binary topology declared via placement links (placementName producers + targetPlacement consumers — the R2.2 sibling-shared owner-name topology) and compiled by the path enumeration: 4095 path-states from 23 graph nodes in ONE pass, forkKey = pathKey on every state, no clone-instance, no after-compile expansion. CORE ONLY + the shared levelCss/cssPropForLevel helpers. The runtime fork-stress-data page above stays alongside as the runtime proof. The DERIVED TRIO (placement / values / link — derived-fork-variants-review §5.1): values-derived · link-derived — the same topology with the per-method component fields on the prototypes (values: every path-state renders its own component-provided value; link: the def chain re-types every level — 4095 elements post the covered-leaf gate, DEFECT #21). Zero clones for every method. The d14 trio (placement · values · link — 27 nodes → 16383 path-states) is the derived family's SCALING PROBE: the d12 enumeration (~2.8s) dominates the d12 totals and hides emit-side scaling; d14 re-exposes it (same per-region pins, the d14 placement page is the d14 family baseline).
  • Fork stress (data-driven) — prototype-driven assembly from a legacy envelope (d2 · d4 · d6 · d8 · d9 · d10 · d11 · d12 · d14) — single-method d12 variants: placement-only · values-only · link-only — plus the d14 SCALING-PROBE variants: placement-only · values-only · link-only — the same deep binary stress tree (2N − 1 nodes, d12 = 4095, d14 = 16383), assembled from a LEGACY envelope alone: preempt-initial-data carries the legacy format (root + two prototype nodes per layer — one per sibling slot) which translateLegacy parses. Each prototype declares its stress-expand after-compile handler by NAME in the data (bodies can't be JSON-serialized); the page supplies the body and recursion does the rest: cloning the layer-1 prototypes onto the root, each clone's inherited handler expanding the next layer via the clone-instance op until depth N. CORE ONLY — no demo-fixtures, no demo-side render machinery; the shared levelCss/cssPropForLevel helpers are pure data-derivation (demo-only, not core APIs).
  • handlers-scenarios — mocked real-world handler scenarios (blind test #5) — ten use-case cards driven ENTIRELY from legacy JSON envelopes: auth dropdown (AUTH-SEAM), comments panel (layer-apply injection), weather card, cart badge, search filter, tabs, form validation, throwing-handler containment, toast + dismiss, multi-handler nodes. Handler bodies ship as function-STRING data; the page module is core-only plumbing (docs/specs/handlers-scenarios.md).
  • hooks-scenarios — the value-provider slot (SPA scenarios) — one SPA envelope with three real-world scenarios driving the HOOKS contract (docs/specs/hooks-map-review.md §7, the value-provider slot): a theme switcher, a user/session panel, and a live counter/badge. Each scenario's controls are authored buttons whose function-STRING bodies write hooks.<name> through the managed channel (clientAPI.apply — never direct node access); the source→target cascade repopulates the consumer readouts. The page checks pin the USER CONTRACT: repeated hook writes never grow the layer stack (one deterministic hook-<name> replace-in-place layer — O(1) after N writes) and the cascade actually re-renders the consumers.
  • hooks-array-scenarios — the rows-mint + cascade (SPA scenarios) — rows minted from a prototype by name (per-row value-bearing source anchors, the node-scoped batch layerId — DEFECT #23); a cross-row consumer resolves the multi-provider fan-out (§9.2 pin 6): both sides of the hook-array cascade.
  • rows-scenarios — the rows-mint demo gate + the def-prototype round trip — the Feature 1/1.5 rows demo gate + the Feature 1a round-trip arm: ONE legacy envelope, a function-STRING mint control, 8 product rows, the fan-out census + linearity pin, and the serialize → loadState → re-mint round trip.
  • markdown-adapter-scenarios — the MarkdownAdapter output (Feature 2) — a legacy JSON envelope rendered through renderProducingProcess(…, MarkdownAdapter): headings, inline content, blockquote, nested-list-in-transparent-container (S17), fenced pre, hr, img — the emitted markdown text asserted via 7 checks.
  • journal-condensing-scenarios — the bounded-journal demo (Feature 3) — a supervisor with maxJournalLength: a state-slice stream exceeds the threshold → the deferred condense rewrites the pre-base entries into ONE base marker; a replay() graph-REPLACEs + re-applies the post-base entries; a post-base undo() operates on the restored graph (D3). 4 checks.
