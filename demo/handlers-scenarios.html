Ten mocked real-world use cases driven ENTIRELY from LEGACY JSON envelopes + the documented core interfaces (translateLegacy → Supervisor → EventBridge → compile → recordResolved → dispatchPhase/dispatchEvent → emitElements / diffMinimal / applyOps (DomAdapter)). Handler bodies are function-STRING data (the seam's (event, context) legacy format); the harness dispatches after-compile on the AUTH-SEAM phase targets and load on every load-bound node at page load, then the runner checks dispatch the rest and assert the spec's intended outputs. The banner is handlers-scenarios; a profile line ([handlers-scenarios:profile]) mirrors the other pages' acc() instrumentation.

Scenario 1 — Auth dropdown: login/profile button + logout (AUTH-SEAM)

The corpus auth pattern through the AUTH-SEAM consumer model: the def userAuth carries {target: 'handlers.afterAssembly', reference: 'AuthInit'} — the N5 carve-out that plans the after-compile PHASE; the chip-slot div type-targets the def; the compiled phase entry copies onto the consumer and the def children (auth button + dropdown menu) re-home in-tree. AuthInit reads the read-only supervisor.userData passthrough: WITHOUT userData the chip converts to the Sign-In LINK (<a href="/api/oauth/login">Sign In</a>) and the dropdown is destroyed-but-retained (walk slot kept, destroyed flag set — its ELEMENT still emits: the def-fill emit sources def children from def data, so a destroyed flag is NOT a render-removal, defects.md OPEN #20; the checks pin the retention half); WITH {username: 'alice'} the chip is the Profile ▼ button and the dropdown survives. The logout control is an AUTHORED header button (the spec's logout button sat inside the def — def-child bindings are a docs-silent dead surface, see the writer notes); its click destroys the dropdown menu (retention) — the page still renders.
