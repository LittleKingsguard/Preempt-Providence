1. **`viable ⊆ slice`.** *Verified: **HOLDS, unconditionally**.* `viable` is built at `src/core/node.ts:1119-1160` by iterating `slice` (`for (const node of slice)` `:1120`) and calling `viable.add(node.id)` only for an element of that iteration (`:1153`, `:1159`). There is no other writer of the set. ∴ every viable id is a slice id, for every slice, including the empty one.
2. **The slice is DESCENDANT-CLOSED under the `children` relation the scan traverses.** *Verified: **HOLDS**.* `focusedSliceFor` computes `S = A*(focus) ∪ D*(focus) [∪ V]`, where `A*` is the `parent`-ward closure (`supervisor.ts:53`), `D*` is the `children`-ward closure (`:54-59`, the **same `get children` relation** the scan uses), and `V` is the conditional provider-universe sweep (`:77-87`), added only when the walk path carries a target and the per-name component Links do not answer (`:60-76`). Each part is descendant-closed: `A*(focus)` because it contains `focus` (whose `D*` is in `S`) and, for every other member, its `D*` is contained in `D*(focus)`; `D*(focus)` trivially; and **`V` because its membership predicate is `n.anchors.some(a => (a.role === 'source' || a.role === 'duplex') && typeof a.target === 'string')` (`supervisor.ts:83`), which is inherited by every descendant produced through a family child anchor** (a child of a provider node carries that same anchor — `Node.addAnchor` copies decl anchors at `node.ts:453-457`/`:480-488`, and family attachment never removes a source/duplex anchor). `get children` = `familyChildAnchors()` (`node.ts:562-582`) sorted by `effectiveOrder` (`:584-593`), i.e. exactly the traversal the scan performs.
   **The report's "downward path-closed" phrasing is REPLACED by this statement** (§0). The distinction is load-bearing: the slice is **NOT** closed under `parent` in every case — `:77-87` adds provider nodes without their ancestors, and `node.parent` (`node.ts:552-560`) reads the *first* child anchor while `children` reads only **non-seam** parent anchors (`node.ts:570`), so a seam-wired def node's `parent` can lie outside the slice. That asymmetry is harmless **because the ancestor arm needs only `viable ⊆ slice`** (fact 1) — every node it can yield a hit from is in the slice — while the descendant arm needs descendant-closure (fact 2).
3. **Consequence (the parity theorem this unit rests on).** For any node `n ∈ S`, `D_S(n) = D(n)`, so a membership-bounded walk from `n` traverses **exactly** the same subtree, in the same pre-order, as the unbounded walk — hence the same eligible (viable) nodes, in the same order. And every visit the bounded walk makes is a visit today's walk makes, so S1 is a **strictly narrower traversal**: `visited_after(n) ≤ visited_before(n)`, with equality only when `D(n) ⊆ S`.
4. **The child relation must be read LIVE.** The slice is built (`focusedSliceFor`) and consumed (`node.compile`) in the same synchronous turn — `supervisor.ts:671-697` loops the dirty set and calls `node.compile(this.focusedSlice(node), …)` with **no `await` between** — so both see identical `get children` results. The confined scan must therefore resolve children through the **same `get children` accessor at walk time**; a cached/precomputed child list (built at slice time or memoized across calls) is a *new state* (§3 S3) and is the one shape that could make the scan's basis diverge from the slice's. This is the reason §2.2 row 6's memoization is out of scope, not merely a perf judgement.

**What a violation looks like.**
- The descendant arm consults a **non-slice** node: observable as a hit/arm/`pathKey`/`forkKey` produced from an id outside the slice (FRS-2, §7).
- The scan is "confined" by iterating the **slice array** instead of descending `children` (a `for (const s of slice) …` rewrite): the **hit ORDER changes** even though the set matches — arm keys `#f:<owner>#<i>` (`node.ts:1287-1292`, `resolve.ts:405-410`) renumber, `bindings`/`trace` order moves, `forkKey`s move (FRS-4/S2, §7).
- The scan is "confined" by checking membership **at yield time only** while still calling `get children` on out-of-slice nodes (a `if (!sliceSet.has(d.id)) continue` placed *after* `stack.push(...d.children)`, or a filter applied post-walk): **parity holds but the measured saving does not** — the `children` traversal `R1` exists to remove survives. Observable as an unchanged per-level Δpass-2 curve (FRS-7, §7).
- A `viable`-set widening (e.g. computing viability over the graph instead of the slice) — that breaks fact 1 and is a **contract break**, not a perf change.

**Status.** **DECIDED** — this is exactly the report's R1 as recommended (`…diagnosis.md:196`, `:215`, `:220`), with the invariant restated in its provable form (§0).

### S2 — hit-set AND hit-ORDER parity · **DECIDED**

**Statement.** For every `(node, name, slice, viable, kinds)` input, the descendant arm's hit array is **element-wise identical** to today's — same length, same `ProviderHit` order (`owner` ids and `anchor` objects in the same positions). **Owning code site / where order is defined and consumed.**

### 7.1 How a PERF unit can be red-first — stated honestly

This unit has **two** assertion families and only one of them can be red before the change:

1. **Scope/behaviour-of-the-walk assertions** — *"the descendant scan consults no node outside the slice"*, *"the walk does not descend into an out-of-slice child"*, *"the walk is strictly narrower than the unscoped traversal on the constructed case"*. These are **RED on the current code**: `src/core/resolve.ts:219` calls `stack.push(...d.children)` with **no membership test**, so the walk demonstrably visits out-of-slice nodes (the report's `6.2 M of 6.49 M` `children` calls are the "before" evidence, `…diagnosis.md:150`, `:196`). They are observed by the test's **own** instrumentation (a counting/recording wrapper over `children`/`parent` installed for the compile only — the `PROBE_COUNTS` technique of the report; **no engine surface is added**, §3 S3), so they need no new API.
2. **Parity assertions** — *"the confined scan returns what the unconfined scan returns"*. These are **GREEN before the change too** (the current behaviour IS the reference), so they cannot be the red half. They are written as **regression guards with frozen goldens** (the `no-clone-invariants` precedent: 5 of its cases shipped "expected GREEN on the current code": `docs/specs/no-clone-invariants.md:947-956`), and they are the half that makes the red half meaningful — a green scope assertion plus a green parity assertion is the unit; a green scope assertion alone could be satisfied by an empty scan.

**Report the red set exactly as that split.** Do NOT invent a failing parity case to manufacture a red: if a parity case fails before the change, that is a **pre-existing defect** and belongs in `docs/defects.md` (§3 S7).
